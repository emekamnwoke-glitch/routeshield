# Scope

| | |
|---|---|
| **Project** | RouteShield |
| **Document version** | 1.0 |
| **Status** | Baseline |

This document defines what RouteShield covers and, more importantly, what it does not. Scope statements that only say what is included are not scope statements.

---

## 1. Architecture scope (Stage One)

### In scope

**Business domain.** The operational response to an unplanned disruption affecting a scheduled urban bus network: detection, impact assessment, option generation, decision, communication, execution and audit.

**Capability coverage.** The four engine capabilities and four output channels established in the baseline concept:

| Engine | Outputs |
|---|---|
| Disruption Detection | Driver Interface |
| Route Optimisation | Passenger Alerts |
| Historical Learning | Control Dashboard |
| Decision Engine | Analytics & Logs |

**Architecture domains.** Business, data, application and technology architecture, each developed to the depth needed to make the next domain decidable — not to exhaustive depth for its own sake.

**Lifecycle coverage.** Preliminary through Phase H, plus continuous requirements management.

**Disruption types.** Road closure, civil protest or blockade, public-order incident, flooding, accident, infrastructure failure, and planned large-scale events treated as pre-known disruptions.

**Time horizon.** Disruptions lasting from minutes to a working day. Multi-day network reconfiguration is a different problem with a different decision cadence.

### Out of scope

- **Scheduled service planning.** Timetabling, route design, frequency setting and network redesign are planning activities on a horizon of months. RouteShield operates on a horizon of minutes and consumes the plan rather than producing it.
- **Fleet maintenance, depot operations and crew rostering.** Adjacent operational domains. RouteShield consumes vehicle availability as an input; it does not manage it.
- **Fare collection, ticketing and revenue protection.** No interaction with the commercial estate.
- **Modes other than bus.** Rail and light rail are named as future development, not current scope. Multimodal disruption response is a materially harder problem and pretending otherwise would weaken the architecture.
- **Autonomous vehicle control.** RouteShield issues instructions to drivers. It does not drive.
- **Safety certification.** The architecture designs for accountability and auditability. It does not constitute a safety case, and no part of this project should be read as one.

## 2. Implementation scope (Stage Two)

### In scope

**MVP disruption lifecycle**, end to end and reproducible:

1. A disruption is created
2. Affected routes, stops and vehicles are identified
3. Alternative stop sequences are generated
4. Alternatives are ranked against a stated objective
5. Stop-skip minimisation is applied as a constraint
6. A controller approves or rejects the recommendation
7. Route state is updated
8. The decision is written to an immutable audit log

**Later increments**, built only once the MVP is complete and stable:

- GPS movement simulation
- Traffic condition simulation
- Driver instruction generation
- Passenger notification generation
- Historical analytics
- ML disruption classification
- Disruption duration prediction
- Learned contingency routes for recurring corridors

**Network data.** Real Dublin bus network topology from open sources — routes, stops, stop sequences, shapes — combined with a road graph derived from OpenStreetMap.

**Disruption data.** Entirely synthetic, generated by a seeded generator in this repository so that any scenario is reproducible from its seed.

### Out of scope

- **Integration with any real operational system.** All external systems are fictional. See [`../02-stage-two-reference-implementation/fictional-operating-model.md`](../02-stage-two-reference-implementation/fictional-operating-model.md).
- **Production deployment.** The demonstrator is a demonstrator. There is no production environment, no on-call, and no service level.
- **Real passenger or driver communication.** Notifications are rendered into the demonstrator's own interface. Nothing is sent to anyone.
- **Real personal data.** No component processes data describing a real individual.
- **Paid infrastructure and paid data.** Constraint C-2 of the charter. This excludes the commercial traffic APIs named in the baseline proposal.
- **Multi-user concurrent control-room operation.** The browser-only deployment target cannot demonstrate it. The architecture addresses it; the implementation does not. This is a stated limitation, not an oversight.

## 3. The Stage One / Stage Two scope boundary

Stage One and Stage Two do not have the same scope, and the difference is deliberate.

Stage One describes the capability an operator would need. Stage Two demonstrates a *subset* of it, under constraints that an operator would not have. The subset is chosen to prove the architecturally interesting parts — the decision path, the optimisation objective, the human-in-the-loop control, the audit trail — rather than the parts that are merely laborious.

Where Stage Two is narrower than Stage One, the gap is recorded rather than quietly closed by trimming Stage One to match. An architecture that shrinks to fit its prototype has stopped being an architecture.

## 4. Assumptions bounding the scope

| # | Assumption |
|---|---|
| SA-1 | An operator in this domain has a control room with authority to alter live services |
| SA-2 | Vehicles report position with sufficient frequency to determine which are affected by a disruption |
| SA-3 | A disruption can be described adequately by a geographic footprint plus a time window |
| SA-4 | Drivers can receive and act on a revised stop sequence during service |

Each of these is carried into the assumptions register with a full classification and justification. SA-3 in particular is a simplification with real consequences — disruptions with fuzzy or moving boundaries, such as a marching protest, are poorly served by a static footprint, and that limitation is inherited by everything downstream of it.

## 5. Explicitly deferred

Recorded so that their absence is visibly a decision rather than an omission:

| Item | Reason for deferral |
|---|---|
| Accessibility weighting in the optimisation objective | Requires a defensible model of stop-level accessibility need, which open data does not provide. Deferred, but flagged in the objective function design as a known gap with equity consequences. |
| Passenger load as a decision input | Requires occupancy data. Synthetic demand is modelled; real-load-driven decisions are not. |
| Controller learning from accept/reject history | Requires a decision corpus the project does not have. |
| Cross-operator coordination | Requires an inter-operator governance model outside the architecture's remit. |
| Formal verification of the routing algorithm | Disproportionate to the project's purpose. |
