## Context

The reference implementation needs a real network to be credible: routes, patterns, stops and a road graph a bus can travel. The baseline proposal named commercial traffic APIs. Constraint C-2 rules out paid data. Everything must be reproducible from public sources.

**Facts** (checked 2026-09-16):
- The National Transport Authority publishes GTFS schedule data for Irish public transport, including Dublin Bus, on data.gov.ie under **Creative Commons Attribution 4.0**, updated daily. A per-operator file list is published alongside the combined feed.
- OpenStreetMap data is published under the **Open Database Licence (ODbL) 1.0**.
- The NTA also publishes GTFS-Realtime, which requires registration for an API key.

## Problem

Where does network data come from, and when is it processed?

## Options considered

### Option 1 — Hand-crafted synthetic network
**For:** Full control; no licence obligations. **Against:** Not Dublin; demonstrates nothing about real topology.

### Option 2 — Fetch GTFS and OSM at runtime in the browser
**For:** Always current. **Against:** Large downloads on every visit; processing in the browser; dependency on third-party availability at demo time; OSM's public APIs have usage policies unsuited to repeated client fetches.

### Option 3 — Fetch and process at build time; ship compact derived files
**For:** Real Dublin network; processing done once with proven tools; derived files are small; the demo does not depend on anyone else's uptime; each build records source URLs, fetch dates and checksums.
**Against:** Data is as fresh as the last build. Attribution and share-alike obligations must be met in the published site.

### Option 4 — Use NTA GTFS-Realtime for live vehicle positions
**For:** Real movement. **Against:** Requires an API key (a secret — impossible in a static site); and it would present real operational data inside a fictional system, blurring the fact/assumption boundary this project depends on.

## Decision

**Option 3** for static network data. **Option 4 rejected.**

The Python pipeline downloads the NTA GTFS feed, filters to Dublin Bus services, derives patterns by grouping identical stop sequences, and extracts a drivable road graph for the Dublin area from OpenStreetMap. It snaps pattern shapes to the road graph, builds the spatial index, and writes versioned compact outputs with a manifest recording source, licence, fetch date and checksum.

Vehicle positions, assignments, road conditions and incidents are **synthetic**, generated by seeded simulators representing the fictional reference systems.

## Rationale

Real topology makes the routing and impact problems genuine; build-time processing keeps the demo fast and self-contained. Rejecting live GTFS-Realtime is a deliberate [P-5](../01-stage-one-architecture/methodology/architecture-principles.md#p-5--distinguish-what-is-known-from-what-is-supposed) decision: real positions flowing through fictional systems would make it impossible for a reader to tell which parts are real.

## Consequences

- **Positive:** real Dublin network; reproducible; no runtime third-party dependency.
- **Negative:** OSM does not reliably describe what a twelve-metre bus can use ([A-008](../02-stage-two-reference-implementation/assumptions.md#a-008)); feasibility will be tagged `verified_open`, never `verified_operator`. Published GTFS is the scheduled network, not the operated one ([A-009](../02-stage-two-reference-implementation/assumptions.md#a-009)).
- **Obligations:** the site and README attribute the NTA (CC BY 4.0) and OpenStreetMap contributors (ODbL); derived network files are made available under ODbL.

## Review trigger

If source URLs or licences change, or if the derived data grows beyond what a static site should ship.
